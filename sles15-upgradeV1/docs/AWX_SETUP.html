Configuración de AWX desde cero

Manual paso a paso para crear en un AWX nuevo (sin nada reutilizable de otro ambiente) todos los objetos necesarios para ejecutar este proyecto: inventario dinámico, credenciales, Project, Job Template y Survey.

Antes de empezar

Resuelto: el plugin ya viaja con este proyecto Ya no depende de que el Execution Environment tenga una Collection instalada: el código del plugin vive versionado en inventory_plugins/excel_inventory.py (raíz del proyecto) y queda habilitado en ansible.cfg ([inventory] enable_plugins). Esto se verificó localmente: Ansible ya lo encuentra y lo invoca correctamente.
Lo único que sigue siendo responsabilidad del Execution Environment El plugin necesita estas librerías de Python instaladas donde corra el Sync del Inventory Source: pandas y openpyxl (siempre), más msal y requests (solo para SharePoint, que es nuestro caso). Si faltan, el plugin lo dice con un mensaje claro (Se requiere 'pandas' para procesar archivos Excel. Instala con: pip install pandas openpyxl) en vez de un error confuso — revisa el log del Sync del paso 5 si esto ocurre.
Variables de entorno requeridas El plugin solo necesita tres: TENANT_ID, CLIENT_ID y CLIENT_SECRET. Son exactamente los tres campos del Credential Type del paso 1.

Por qué ya no se usa Limit Decisión explícita del usuario para este ambiente: el host a tocar se elige con el match CRQ + Lote + Ambiente del Survey (sección 7) contra esas mismas columnas del inventario — no con Limit. Cada ejecución (incluso un precheck) corresponde a un CRQ/RFC real de control de cambios, así que ese dato ya identifica el host sin necesitar un campo aparte. Si ningún host del inventario coincide con los 3 valores declarados, el playbook falla explícito antes de tocar cualquier host (ver playbooks/upgrade.yml).
7

Survey

En el mismo Job Template → pestaña Survey → activar Survey Enabled. Cada pregunta tiene un campo "Description" en AWX (texto de ayuda que ve el operador al llenar el formulario) — el texto sugerido va en la última columna, listo para copiar.

upgrade_crq / upgrade_lote / upgrade_ambiente ya no son solo trazabilidad Estos 3 campos son ahora el único mecanismo de selección de hosts del proyecto (reemplazan a Limit, sección 6): deben marcarse Required en AWX, y su valor debe coincidir EXACTAMENTE (mismas mayúsculas/minúsculas, sin espacios extra) con las columnas CRQ/ Lote/Ambiente del Excel para el host que se quiere tocar. Si no coinciden con ningún host, el Job falla explícito con el mensaje exacto de qué se buscó.
PreguntaVariableTipoDescription (pegar en AWX)
Modo de ejecución upgrade_mode Selección múltiple: precheck, validate, sp4_to_sp5, sp5_to_sp6, sp6_to_sp7, full precheck: solo diagnostica (SO, espacio, servicios, GeoPOS, repos actuales). No modifica nada. validate: además contacta de verdad los repos Foreman del destino (metadata/TLS/CA/GPG, simulación de la actualización). Tampoco modifica nada. sp4_to_sp5 / sp5_to_sp6 / sp6_to_sp7: ejecutan esa única etapa real, con reinicio incluido — requieren confirm_production_upgrade en true. full: encadena SP5→SP6 y, solo si esa etapa quedó realmente validada (dup aplicado, reiniciado, Service Pack confirmado, servicios críticos y GeoPOS críticos OK), continúa con SP6→SP7 — nunca incluye SP4→SP5, que siempre se ejecuta aparte con sp4_to_sp5.
¿Confirma ejecución real en producción? confirm_production_upgrade Selección múltiple, con exactamente dos opciones: true y false (ver nota abajo) Obligatorio para los modos reales (sp4_to_sp5, sp5_to_sp6, sp6_to_sp7, full). Si el Modo de ejecución es precheck o validate, este valor se ignora por completo, sea true o false — esos dos modos nunca modifican el servidor bajo ninguna combinación. Déjalo en false para solo diagnosticar/ensayar un modo real. Ponlo en true únicamente cuando quieras aplicar la migración real, con reinicio incluido. Es independiente del Ambiente seleccionado abajo: todos los servidores de este proyecto se tratan como productivos, sin excepción.
Ingrese el CRQ/RFC upgrade_crq Texto, Required Debe coincidir exactamente con la columna CRQ del inventario del host que se quiere tocar. Selecciona el/los host(s) de esta ejecución junto con Lote y Ambiente — si no coincide con ninguno, el Job falla explícito.
Seleccione el Lote a parchar del CRQ/RFC upgrade_lote Texto o Selección múltiple, Required Debe coincidir exactamente con la columna Lote del inventario del host que se quiere tocar. Selecciona el/los host(s) de esta ejecución junto con CRQ y Ambiente — si no coincide con ninguno, el Job falla explícito.
Seleccione el Ambiente asociado al CRQ/RFC y Lote upgrade_ambiente Selección múltiple: Producción / Desarrollo / Laboratorio / Staging, Required Debe coincidir exactamente con la columna Ambiente del inventario del host que se quiere tocar. Selecciona el/los host(s) de esta ejecución junto con CRQ y Lote. NO reemplaza ni relaja "confirm_production_upgrade": todos los servidores de este proyecto se tratan como productivos, sin importar el Ambiente seleccionado aquí.
Por qué existe confirm_production_upgrade si upgrade_mode ya dice que se quiere migrar No es redundante: es el patrón de "dos llaves". upgrade_mode decide qué operación correría; confirm_production_upgrade decide si esa operación realmente se ejecuta, o se queda preparada pero bloqueada. Hacen falta las dos para modificar un servidor real:
  • Protege contra un valor guardado por defecto: si un Job Template o un Schedule queda configurado con upgrade_mode: full, esa ejecución sigue sin modificar nada mientras no se active explícitamente confirm_production_upgrade: true en ese lanzamiento puntual.
  • Es independiente de Ambiente a propósito: no se puede usar el Ambiente como candado porque todos los hosts de este proyecto se tratan como productivos sin importar el Ambiente — hace falta un campo que no dependa de ningún dato del inventario.
  • Es un único punto de control en el código (playbooks/tasks/run_stage.yml), revisado antes de tocar cualquier repositorio o paquete, igual para los 4 modos reales — para auditoría es una sola pregunta uniforme en vez de confiar en que elegir el modo correcto nunca fue un error de click.
Por defecto siempre es false, así que cualquier ejecución que no lo active a propósito queda inofensiva aunque el resto del Survey esté mal configurado.
Importante: AWX no tiene un tipo de pregunta "Booleano" Usa Selección múltiple con las opciones escritas literalmente true y false (en inglés, en minúsculas — no "Sí"/"No", ni con mayúscula inicial). El código del playbook convierte este valor con el filtro | bool de Ansible, que solo reconoce true/false, yes/no, on/off, 1/0 (sin distinguir mayúsculas) — cualquier otro texto hace que la etapa se bloquee explícitamente (fail-closed) en vez de interpretarse mal. Marcar false como valor por defecto.
Por qué el prefijo upgrade_ El inventario dinámico (paso 5) ya expone crq/lote/ ambiente como variables de host (del último ciclo de parchado registrado en la hoja). Usar los mismos nombres en el Survey haría que un host heredara silenciosamente ese dato viejo en el reporte de este upgrade. Ver playbooks/group_vars/all.yml.

9

Workflow Job Template (opcional: por etapas)

Todo lo anterior (secciones 1-8) ya es suficiente para operar el proyecto con un solo Job Template. Esta sección es una alternativa opcional: partir la misma ejecución en 4 Job Templates encadenados por un Workflow Job Template, para ver cada etapa como un nodo separado en el diagrama, poder reintentar solo la etapa que falló, y poder insertar un Approval Node entre "preparar" y "aplicar" (útil para exigir aprobación de un supervisor antes del cambio real). No reemplaza nada de lo anterior: reutiliza el mismo Project/Inventory/Credential, y el mismo playbook playbooks/upgrade.yml para 3 de los 4 nodos.

9.1 La variable upgrade_phase

Nueva variable (playbooks/group_vars/all.yml) que permite correr una etapa real en 2 pasos separados en vez de todo de una vez:

ValorQué hace
both (default)Todo en una sola corrida, exactamente como en las secciones 1-8 (sin Workflow).
prepareBackup + deshabilitar preexistentes + repos ORIGEN + updatestack (real) + repos DESTINO agregados y verificados. Se detiene ahí — sin dup -D, dup ni reinicio. El sistema SÍ queda modificado (requiere confirm_production_upgrade igual que both).
applyVerifica (gate) que los repos DESTINO de una fase prepare previa sigan exactamente habilitados — si no, falla explícito pidiendo ejecutar primero "preparar". Luego dup -D → dup real → reinicio → validación → limpieza.
upgrade_mode: full es la única excepción full encadena SP5→SP6 y SP6→SP7, cada uno con su propio set de repos — no existe un único momento de "preparar" válido para ambos saltos a la vez. Por eso, si upgrade_mode=full, el código (_effective_upgrade_phase en playbooks/tasks/run_stage.yml) ignora upgrade_phase y hace todo junto (como both) — excepto en el nodo "Preparar repos", donde con full no hace absolutamente nada (no modifica el sistema, solo informa) para que un único diseño de Workflow sirva tanto para un salto individual como para full, sin que full dispare un dup real por error en el nodo que se supone que solo prepara.

9.2 Los 4 Job Templates

Mismo Inventory/Project/Credential que la sección 6. upgrade_crq/ upgrade_lote/upgrade_ambiente/confirm_production_upgrade se marcan "Prompt on Launch" en los 4 (heredan la respuesta del Survey del Workflow, sección 9.4). upgrade_mode se marca "Prompt on Launch" solo en los nodos 2 y 3 (en el nodo 1 queda fijo en precheck; el nodo 4 no lo usa).

#NamePlaybookExtra vars fijas (NO prompt)
1SLES Upgrade - 1 Precheckplaybooks/upgrade.ymlupgrade_mode: precheck
2SLES Upgrade - 2 Preparar reposplaybooks/upgrade.ymlupgrade_phase: prepare
3SLES Upgrade - 3 Aplicarplaybooks/upgrade.ymlupgrade_phase: apply
4SLES Upgrade - 4 Reportingplaybooks/report_summary.yml(ninguna)
Nodo 4: por qué un playbook distinto playbooks/report_summary.yml es la misma consolidación (resumen.html) que ya corre automáticamente al final de playbooks/upgrade.yml en cualquier modo — se extrajo a su propio archivo justo para que este nodo pueda apuntar ahí directamente, sin duplicar esa lógica en dos lugares. No necesita Survey ni CRQ/Lote/Ambiente: solo lee reports/run_summary.jsonl y renderiza el resumen.

9.3 El Workflow Job Template

Resources → Templates → Add → Workflow Job Template → pestaña "Workflow Visualizer" → encadenar los 4 nodos:

EnlaceCondición
Nodo 1 (Precheck) → Nodo 2 (Preparar repos)On Success
Nodo 2 (Preparar repos) → Nodo 3 (Aplicar)On Success (aquí se puede insertar un Approval Node intermedio)
Nodo 3 (Aplicar) → Nodo 4 (Reporting)Always (no "On Success")
Por qué el último enlace es "Always" y no "On Success" Si el Nodo 3 falla, igual se quiere el resumen consolidado al día (para ver el fallo sin conectarse por SSH ni leer el log del Job) — "On Success" dejaría el reporte desactualizado justo cuando más se necesita.

9.4 Survey del Workflow

El Survey se configura en el Workflow Job Template (no en cada nodo): mismas 5 preguntas de la sección 7 (upgrade_mode, confirm_production_upgrade, upgrade_crq, upgrade_lote, upgrade_ambiente). Las respuestas se propagan a cada nodo que tenga esa variable marcada "Prompt on Launch" (sección 9.2).

9.5 Notificaciones (por ejemplo, a un canal de Teams)

No requiere ningún cambio de código: se configuran como Notification Templates nativas de AWX (Administration → Notifications → Add, tipo "Webhook"), asociadas al Workflow Job Template (para notificar el resultado de todo el pipeline) o al Nodo 4 específicamente. El webhook real del canal de Teams es responsabilidad del administrador de AWX — este proyecto no lo invoca directamente.
