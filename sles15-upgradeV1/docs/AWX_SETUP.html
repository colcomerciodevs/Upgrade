Configuración de AWX desde cero

Manual paso a paso para crear en un AWX nuevo (sin nada reutilizable de otro ambiente) todos los objetos necesarios para ejecutar este proyecto: inventario dinámico, credenciales, Project, Survey y el Workflow Job Template de 5 etapas (configuración por defecto).
0. Antes de empezar 1. Credential Type 2. Credential (Excel) 3. Credential (SSH) 4. Project 5. Inventory 6. Survey 7. Workflow (por defecto) 8. Alternativa: 1 solo Job Template 9. Primera prueba
0

Antes de empezar

Resuelto: el plugin ya viaja con este proyecto Ya no depende de que el Execution Environment tenga una Collection instalada: el código del plugin vive versionado en inventory_plugins/excel_inventory.py (raíz del proyecto) y queda habilitado en ansible.cfg ([inventory] enable_plugins). Esto se verificó localmente: Ansible ya lo encuentra y lo invoca correctamente.
Lo único que sigue siendo responsabilidad del Execution Environment El plugin necesita estas librerías de Python instaladas donde corra el Sync del Inventory Source: pandas y openpyxl (siempre), más msal y requests (solo para SharePoint, que es nuestro caso). Si faltan, el plugin lo dice con un mensaje claro (Se requiere 'pandas' para procesar archivos Excel. Instala con: pip install pandas openpyxl) en vez de un error confuso — revisa el log del Sync del paso 5 si esto ocurre.
Variables de entorno requeridas El plugin solo necesita tres: TENANT_ID, CLIENT_ID y CLIENT_SECRET. Son exactamente los tres campos del Credential Type del paso 1.

6

Survey (preguntas compartidas por las 5 etapas)

Estas 5 preguntas son las mismas en todo el proyecto. En la configuración por defecto (paso 7, Workflow) se crean una sola vez, en el Workflow Job Template, y se propagan a cada etapa que las necesite. Cada pregunta tiene un campo "Description" en AWX (texto de ayuda que ve el operador al llenar el formulario) — el texto sugerido va en la última columna, listo para copiar.

Por qué no existe un campo "Limit" Decisión explícita del usuario para este ambiente: el host a tocar se elige con el match CRQ + Lote + Ambiente (preguntas de abajo) contra esas mismas columnas del inventario — nunca con el campo nativo Limit de AWX. Por eso, en ninguno de los Job Templates de este proyecto (paso 7 u 8) se marca Limit como "Prompt on Launch": se deja siempre vacío. Cada ejecución (incluso un precheck) corresponde a un CRQ/RFC real de control de cambios, así que ese dato ya identifica el host sin necesitar un campo aparte. Si ningún host del inventario coincide con los 3 valores declarados, el playbook falla explícito antes de tocar cualquier host (ver playbooks/upgrade.yml).
Por qué "Modo de ejecución" en el Workflow NO incluye precheck/validate En el Workflow (configuración por defecto), el Nodo 1 ya ejecuta precheck siempre, automáticamente, sin que el operador tenga que elegirlo — y validate no participa en este Workflow en absoluto (es un chequeo independiente, de solo lectura, pensado para ejecuciones programadas de monitoreo rutinario, no para una migración). Ofrecer esas 2 opciones en el Survey del Workflow sería confuso: si alguien las eligiera, los nodos 2 y 3 (Preparar/Aplicar) simplemente no tendrían ningún salto real que preparar o aplicar. Por eso, ahí la pregunta solo debe tener las 4 opciones que SÍ consumen los nodos 2 y 3: sp4_to_sp5, sp5_to_sp6, sp6_to_sp7, full. La alternativa simplificada (sección 8) sí necesita las 6, porque ahí un único Job Template cubre los 6 modos.
upgrade_crq / upgrade_lote / upgrade_ambiente ya no son solo trazabilidad Estos 3 campos son el único mecanismo de selección de hosts del proyecto: deben marcarse Required en AWX, y su valor debe coincidir EXACTAMENTE (mismas mayúsculas/minúsculas, sin espacios extra) con las columnas CRQ/Lote/Ambiente del Excel para el host que se quiere tocar. Si no coinciden con ningún host, el Job falla explícito con el mensaje exacto de qué se buscó.
PreguntaVariableTipoDescription (pegar en AWX)
Modo de ejecución upgrade_mode Selección múltiple — las opciones dependen de dónde se crea esta pregunta (ver callout debajo de la tabla):
En el Workflow (sección 7, configuración por defecto): solo sp4_to_sp5, sp5_to_sp6, sp6_to_sp7, full (4 opciones).
En la alternativa simplificada (sección 8): las 6 opciones, agregando precheck y validate. 		sp4_to_sp5 / sp5_to_sp6 / sp6_to_sp7: ejecutan esa única etapa real, con reinicio incluido — requieren confirm_production_upgrade en true. full: encadena SP5→SP6 y, solo si esa etapa quedó realmente validada (dup aplicado, reiniciado, Service Pack confirmado, servicios críticos y GeoPOS críticos OK), continúa con SP6→SP7 — nunca incluye SP4→SP5, que siempre se ejecuta aparte con sp4_to_sp5. (Si esta pregunta incluye precheck/validate -- alternativa simplificada --: precheck solo diagnostica, validate además contacta de verdad los repos Foreman del destino; ninguno de los dos modifica repositorios ni paquetes -- la única excepción es que ambos pueden instalar la CA interna si todavía no está presente, operación idempotente, ver docs/ARQUITECTURA_Y_DISENO_TECNICO.html sección 1.)
¿Confirma ejecución real en producción? confirm_production_upgrade Selección múltiple, con exactamente dos opciones: true y false (ver nota abajo) Obligatorio para los modos reales (sp4_to_sp5, sp5_to_sp6, sp6_to_sp7, full). Si el Modo de ejecución es precheck o validate, este valor se ignora por completo, sea true o false — esos dos modos nunca modifican repositorios ni paquetes bajo ninguna combinación (la única excepción es instalar la CA interna si faltaba, operación idempotente). Déjalo en false para solo diagnosticar/ensayar un modo real. Ponlo en true únicamente cuando quieras aplicar la migración real, con reinicio incluido. Es independiente del Ambiente seleccionado abajo: todos los servidores de este proyecto se tratan como productivos, sin excepción.
Ingrese el CRQ/RFC upgrade_crq Texto, Required Debe coincidir exactamente con la columna CRQ del inventario del host que se quiere tocar. Selecciona el/los host(s) de esta ejecución junto con Lote y Ambiente — si no coincide con ninguno, el Job falla explícito.
Seleccione el Lote a parchar del CRQ/RFC upgrade_lote Texto o Selección múltiple, Required Debe coincidir exactamente con la columna Lote del inventario del host que se quiere tocar. Selecciona el/los host(s) de esta ejecución junto con CRQ y Ambiente — si no coincide con ninguno, el Job falla explícito.
Seleccione el Ambiente asociado al CRQ/RFC y Lote upgrade_ambiente Selección múltiple: Producción / Desarrollo / Laboratorio / Staging, Required Debe coincidir exactamente con la columna Ambiente del inventario del host que se quiere tocar. Selecciona el/los host(s) de esta ejecución junto con CRQ y Lote. NO reemplaza ni relaja "confirm_production_upgrade": todos los servidores de este proyecto se tratan como productivos, sin importar el Ambiente seleccionado aquí.
Por qué existe confirm_production_upgrade si upgrade_mode ya dice que se quiere migrar No es redundante: es el patrón de "dos llaves". upgrade_mode decide qué operación correría; confirm_production_upgrade decide si esa operación realmente se ejecuta, o se queda preparada pero bloqueada. Hacen falta las dos para modificar un servidor real:
  • Protege contra un valor guardado por defecto: si un Job Template o un Schedule queda configurado con upgrade_mode: full, esa ejecución sigue sin modificar nada mientras no se active explícitamente confirm_production_upgrade: true en ese lanzamiento puntual.
  • Es independiente de Ambiente a propósito: no se puede usar el Ambiente como candado porque todos los hosts de este proyecto se tratan como productivos sin importar el Ambiente — hace falta un campo que no dependa de ningún dato del inventario.
  • Es un único punto de control en el código (playbooks/tasks/run_stage.yml), revisado antes de tocar cualquier repositorio o paquete, igual para los 4 modos reales — para auditoría es una sola pregunta uniforme en vez de confiar en que elegir el modo correcto nunca fue un error de click.
Por defecto siempre es false, así que cualquier ejecución que no lo active a propósito queda inofensiva aunque el resto del Survey esté mal configurado.
Importante: AWX no tiene un tipo de pregunta "Booleano" Usa Selección múltiple con las opciones escritas literalmente true y false (en inglés, en minúsculas — no "Sí"/"No", ni con mayúscula inicial). El código del playbook convierte este valor con el filtro | bool de Ansible, que solo reconoce true/false, yes/no, on/off, 1/0 (sin distinguir mayúsculas) — cualquier otro texto hace que la etapa se bloquee explícitamente (fail-closed) en vez de interpretarse mal. Marcar false como valor por defecto.
Por qué el prefijo upgrade_ El inventario dinámico (paso 5) ya expone crq/lote/ ambiente como variables de host (del último ciclo de parchado registrado en la hoja). Usar los mismos nombres en el Survey haría que un host heredara silenciosamente ese dato viejo en el reporte de este upgrade. Ver playbooks/group_vars/all.yml.
7

Workflow Job Template — configuración por defecto

Esta es la forma recomendada y por defecto de operar el proyecto en AWX: partir la ejecución en 5 Job Templates encadenados por un Workflow Job Template. Cada etapa queda como un nodo visible en el diagrama, se puede reintentar solo la que falló, y se puede insertar un Approval Node entre "preparar" y "aplicar" (para exigir aprobación de un supervisor antes del cambio real). Si se necesita algo más simple — por ejemplo, para un laboratorio rápido sin punto de aprobación — existe una alternativa con un solo Job Template (paso 8), con el mismo código y el mismo Survey.

7.1 La variable upgrade_phase

Es lo que hace posible partir una etapa real en 2 pasos (playbooks/group_vars/all.yml):

ValorQué haceDónde se usa
prepareBackup + deshabilitar preexistentes + repos ORIGEN + updatestack (real) + repos DESTINO agregados y verificados. Se detiene ahí — sin dup -D, dup ni reinicio. El sistema SÍ queda modificado (requiere confirm_production_upgrade).Nodo 2 (7.3)
applyVerifica (gate) que los repos DESTINO de una fase prepare previa sigan exactamente habilitados — si no, falla explícito pidiendo ejecutar primero "preparar". Luego dup -D → dup real → reinicio → validación → limpieza.Nodo 3 (7.4)
both (default si se omite)Todo en una sola corrida. No se usa en ningún nodo del Workflow — es lo que usa la alternativa de un solo Job Template (paso 8).Paso 8
upgrade_mode: full es la única excepción full encadena SP5→SP6 y SP6→SP7, cada uno con su propio set de repos — no existe un único momento de "preparar" válido para ambos saltos a la vez. Por eso, si upgrade_mode=full, el código (_effective_upgrade_phase en playbooks/tasks/run_stage.yml) ignora upgrade_phase y hace todo junto (como both) — excepto en el nodo 2 "Preparar repos", donde con full no hace absolutamente nada (no modifica el sistema, solo informa) para que el mismo Workflow sirva tanto para un salto individual como para full, sin que full dispare un dup real por error en el nodo que se supone que solo prepara.

Confirmado contra un AWX real: el Survey del Workflow SIEMPRE le gana al valor guardado en el Job Template El diseño original (sección 7.2, versión anterior) intentaba fijar upgrade_mode: precheck en el Nodo 1 vía "Prompt on Launch" + un override de nodo. Se probó en un AWX real y no funcionó: el Job del Nodo 1 corrió con upgrade_mode: sp5_to_sp6 (el valor del Survey, pensado para los Nodos 2/3), no con precheck. En AWX, cuando "Prompt on Launch" está activado, cualquier valor que llegue desde afuera (Survey, API) siempre reemplaza lo guardado en el Job Template — ese es justamente el propósito de esa casilla. Por eso el Nodo 1 ahora usa un playbook dedicado (playbooks/precheck_only.yml) que ni siquiera lee upgrade_mode: no hay variable que pueda colisionar. Armar el diagrama: agregar y encadenar los 5 nodos

El Visualizer arranca con un único recuadro llamado START. Todo se construye haciendo clic en el símbolo "+" que aparece sobre un recuadro ya puesto (empezando por START) para agregar el siguiente paso.

  1. Clic en el "+" de START → se abre un panel "Add Node" → pestaña Job Templates → seleccionar SLES Upgrade - 1 Precheck (7.2) → Select → Save. Queda agregado como primer nodo, enlazado desde START.
  2. Clic en el "+" que ahora aparece sobre el Nodo 1 → elegir SLES Upgrade - 2 Preparar repos → Select → Save. AWX dibuja el enlace Nodo 1 → Nodo 2 con la condición por defecto On Success (correcta, no hay que cambiarla).
  3. Clic en el "+" sobre el Nodo 2 → elegir SLES Upgrade - 3 Aplicar → Select → Save (enlace Nodo 2 → Nodo 3, también On Success por defecto).
    Aquí es donde se inserta el Approval Node (opcional) En vez de conectar el Nodo 2 directamente con el Nodo 3, se puede intercalar un nodo de aprobación: clic en el "+" sobre el Nodo 2 → pestaña Approval (en el mismo panel "Add Node", junto a "Job Templates") → darle un Name (ej. Aprobar aplicar upgrade) y un Timeout opcional → Save. Luego, desde ese nodo de aprobación, se agrega el Nodo 3 con su propio "+", igual que los pasos anteriores. El Job queda detenido en ese punto hasta que alguien con permiso lo apruebe o lo rechace desde la vista del Job en ejecución.
  4. Clic en el "+" sobre el Nodo 3 → elegir SLES Upgrade - 4 Reporting → Select → Save. Por defecto el enlace queda en "On Success" — hay que cambiarlo: clic en la línea del enlace Nodo 3 → Nodo 4 → se abre un selector con 3 opciones (On Success / On Failure / Always) → elegir Always → Save.
  5. Clic en el "+" sobre el Nodo 4 → elegir SLES Upgrade - 5 Sincronizar SharePoint → Select → Save. Igual que el enlace anterior, por defecto queda en "On Success" — cambiarlo a Always de la misma forma (clic en la línea del enlace Nodo 4 → Nodo 5).
  6. Clic en "Save" (arriba del Visualizer, no el de cada nodo) para guardar el diagrama completo.

Nodo 4 (Reporting) → Nodo 5 (Sincronizar SharePoint)Always (igual, cambiar a mano)
Por qué esos 2 últimos enlaces son "Always" y no "On Success" Si el Nodo 3 falla, igual se quiere el resumen consolidado al día (para ver el fallo sin conectarse por SSH ni leer el log del Job) — "On Success" dejaría el reporte desactualizado justo cuando más se necesita. Por la misma razón, el Nodo 5 debe sincronizar a SharePoint incluso cuando algo falló antes: el reporte de un fallo es tan importante de tener disponible como el de un éxito.

7.4 Survey: se crea en el Workflow Job Template

En el Workflow Job Template (no en cada nodo) → pestaña Survey → activar Survey Enabled → crear las 5 preguntas de la sección 6. Las respuestas se propagan automáticamente, al lanzar, a cada nodo que tenga activado su checkbox "Prompt on Launch" junto a Variables (7.2) — sin necesitar ningún ajuste adicional por variable.

7.5 Notificaciones (por ejemplo, a un canal de Teams)

No requiere ningún cambio de código: se configuran como Notification Templates nativas de AWX (Administration → Notifications → Add, tipo "Webhook"), asociadas al Workflow Job Template (para notificar el resultado de todo el pipeline) o al Nodo 4 específicamente. El webhook real del canal de Teams es responsabilidad del administrador de AWX — este proyecto no lo invoca directamente.
