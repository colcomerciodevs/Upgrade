Configuración de AWX desde cero

Manual paso a paso para crear en un AWX nuevo (sin nada reutilizable de otro ambiente) todos los objetos necesarios para ejecutar este proyecto: inventario dinámico, credenciales, Project, Job Template y Survey.
0. Antes de empezar 1. Credential Type 2. Credential (Excel) 3. Credential (SSH) 4. Project 5. Inventory 6. Job Template 7. Survey 8. Primera prueba
0

Antes de empezar

Verificar primero — bloqueante El plugin de inventario personalizado excel_inventory (el código que implementa source_type: sharepoint, lee el Excel vía Graph API, etc.) debe estar disponible en el Execution Environment que usará este AWX nuevo. Si este AWX es distinto al que ya usan para parchado, ese EE probablemente no lo tiene instalado todavía. Sin esto, el paso 5 (Inventory Source) fallará sin importar qué tan bien esté configurado lo demás. Pregunta a quien mantiene el AWX de parchado de dónde sale ese plugin (EE propio, Collection, paquete).
Variables de entorno reales vs. las de tu .env inventory/linux_excel_inventory.yml solo referencia explícitamente TENANT_ID, CLIENT_ID y CLIENT_SECRET (vía lookup('env', ...)). Tu .env tiene más variables (remote_user, remote_host, remote_pass, etc.) que probablemente usa el código interno del plugin u otro script de parchado — no se inventaron aquí porque no se confirmó el código fuente del plugin. Si el Sync del paso 5 se queja de una variable de entorno faltante, agrégala al Credential Type del paso 1 con el mismo patrón.

Credential Type personalizado

Administration → Credential Types → Add

Input configuration:

fields:
  - id: tenant_id
    type: string
    label: Tenant ID
  - id: client_id
    type: string
    label: Client ID
  - id: client_secret
    type: string
    label: Client Secret
    secret: true
required:
  - tenant_id
  - client_id
  - client_secret

Injector configuration:

env:
  TENANT_ID: '{{ tenant_id }}'
  CLIENT_ID: '{{ client_id }}'
  CLIENT_SECRET: '{{ client_secret }}'

Por qué Limit y no un campo de Survey El host a tocar se elige siempre con Limit (marcado "Prompt on Launch"), nunca con un campo de Survey tipo "IP del servidor" — evita tener dos lugares definiendo lo mismo. Ver ARQUITECTURA_Y_DISENO_TECNICO.html, sección 8.

Survey

En el mismo Job Template → pestaña Survey → activar Survey Enabled.

PreguntaVariableTipo
Modo de ejecuciónupgrade_modeMultiple Choice: precheck, validate, sp4_to_sp5, sp5_to_sp6, sp6_to_sp7, full
¿Confirma ejecución real en producción?confirm_production_upgradeBoolean
Ingrese el CRQ/RFCupgrade_crqText (opcional)
Seleccione el Lote a parchar del CRQ/RFCupgrade_loteText u opción múltiple (opcional)
Seleccione el Ambiente asociado al CRQ/RFC y Loteupgrade_ambienteMultiple Choice: Producción / Desarrollo / Laboratorio / Staging (opcional)
Por qué el prefijo upgrade_ El inventario dinámico (paso 5) ya expone crq/lote/ ambiente como variables de host (del último ciclo de parchado registrado en la hoja). Usar los mismos nombres en el Survey haría que un host heredara silenciosamente ese dato viejo en el reporte de este upgrade. Ver playbooks/group_vars/all.yml.
